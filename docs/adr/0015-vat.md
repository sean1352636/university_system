# 0015 — VAT (UK)

**Date:** 2026-05-08
**Status:** Proposed (data layer partially implemented in 8.117.118)

---

## Context

Item #4 from the finance-system Tier-1 gap survey (2026-05-07).

UK universities are **partially exempt** for VAT purposes. Most core
education activity is exempt (tuition, qualifying research grants,
catering provided to students); commercial activities attract VAT
(conferences, accommodation for non-students, consultancy income,
charity-shop retail, room hire to external organisations). HMRC's
Making Tax Digital (MTD) regime requires VAT-registered organisations
to submit returns through approved software via API, not through the
HMRC web portal.

### What 8.117.118 already delivered

The data layer and per-transaction posting is done:

- **Schema migration**: `vat_rate` (TEXT) and `vat_amount` (REAL)
  columns added to `payments` and `unified_refunds`. Existing rows
  default to NULL and post under the previous (no-VAT) behaviour.
- **GL accounts**: `1300 VAT Input` and `2200 VAT Output` exist in
  the seeded SORP chart.
- **Classification map** keyed by `source_type` in
  `posting.py:_VAT_DEFAULT_BY_SOURCE`: tuition / club / library /
  housing → exempt; restaurant / cafe / takeaway / shop / gym etc.
  → standard 20%; train → zero-rated; bank_topup → exempt (not a
  supply).
- **3-line GL split** for standard-rated supplies (`Dr Cash gross /
  Cr Revenue net / Cr 2200 VAT Output`) and the reverse on refunds.
  Exempt and zero-rated supplies post the unchanged 2-line journal.
- **Override path**: per-row `vat_rate`/`vat_amount` on the
  operational row takes precedence over the default classification.
- **Test coverage**: 7 VAT tests in `test_ledger.py` covering the
  matrix above, plus a live-DB smoke test confirming a £120
  restaurant payment splits to £100 net + £20 VAT.

The output-VAT trail to account 2200 is therefore live for any
commerce activity from 8.117.118 onward.

### What's still missing

1. **Partial-exemption calculation.** Universities can recover input
   VAT only in proportion to their taxable activity. The recovery
   percentage is determined by the year-end "de minimis" or a
   special method agreed with HMRC. Currently all input VAT (when
   it eventually flows) would land on 1300 with no proportional
   adjustment.
2. **Input VAT on the AP side.** Depends on ADR 0014 (Accounts
   Payable). 1300 VAT Input has zero balance today because nothing
   posts there.
3. **Quarterly VAT return assembly.** No code reads from the GL to
   produce the 9-box return numbers.
4. **MTD HMRC API integration.** No OAuth flow, no signed JSON
   submission, no retrieval of submitted returns.
5. **Per-source classification review.** The 8.117.118 defaults are
   conservative starting points. Some need finance-staff sign-off:
   - Conferences (currently no source_type — would default to exempt
     via `general`; should be standard for external conferences)
   - Room hire (no source_type — depends on counterparty)
   - Research grants (currently exempt by default; specific HMRC
     rules apply per funder type)
   - Adult-education / CPD courses (treatment depends on whether
     classed as "education" or "vocational training")
6. **Reduced-rate (5%) handling.** Schema supports it (`vat_rate =
   'reduced'`), but no source defaults to it. Energy bills coming
   through AP would be reduced rate.
7. **Backfill.** Existing journals stay as posted (single revenue
   line); only post-8.117.118 activity has VAT split. The trial
   balance "VAT Output" reflects only forward-going activity.
8. **VAT on imports / reverse charge.** Services bought from non-UK
   suppliers require accounting for output AND input VAT on the
   same import. Tied up with AP and multi-currency (ADR 0016).
9. **Margin scheme** for the charity shop (second-hand goods VAT
   margin scheme). Possibly applicable; needs confirmation.

### Alternatives considered

1. **Spreadsheet-based quarterly returns.** Many small UK
   organisations export GL data to Excel and produce returns
   manually. Becomes legally non-compliant once MTD-registered.
2. **External VAT bridging software** (e.g. Avalara, BTC Software).
   Fine but adds licensing + integration cost; the 9-box assembly
   from a clean GL is not technically hard.
3. **Build the remaining VAT layer in this codebase.** Chosen
   approach below.

## Decision

We will complete VAT support in **three sequential phases**, each
deliverable on its own:

### Phase 1 — Quarterly return assembly (no HMRC API)

Adds the assembly logic that produces the UK VAT return Boxes 1–9
from the GL. Output is an audit-ready report; submission is still
manual (HMRC web portal or external bridging software).

**New tables:**

```sql
CREATE TABLE vat_returns (
    return_id      INTEGER PRIMARY KEY AUTOINCREMENT,
    period_key     TEXT    NOT NULL UNIQUE,    -- HMRC's period_key (e.g. '24A4')
    period_start   TEXT    NOT NULL,
    period_end     TEXT    NOT NULL,
    box_1          REAL    NOT NULL,           -- VAT due on sales
    box_2          REAL    NOT NULL,           -- VAT due on EU acquisitions
    box_3          REAL    NOT NULL,           -- Total VAT due (box_1 + box_2)
    box_4          REAL    NOT NULL,           -- VAT reclaimed on purchases
    box_5          REAL    NOT NULL,           -- Net VAT (box_3 - box_4)
    box_6          REAL    NOT NULL,           -- Total sales ex-VAT
    box_7          REAL    NOT NULL,           -- Total purchases ex-VAT
    box_8          REAL    NOT NULL,           -- Total EU goods supplied ex-VAT
    box_9          REAL    NOT NULL,           -- Total EU goods acquired ex-VAT
    status         TEXT    NOT NULL DEFAULT 'draft'
                     CHECK (status IN ('draft','final','submitted','accepted')),
    finalised_at   TEXT,
    finalised_by   TEXT,
    submitted_at   TEXT,
    submission_reference TEXT,                  -- HMRC return reference once submitted
    created_at     TEXT    NOT NULL DEFAULT (datetime('now'))
);
```

**Service surface:**

```python
def init_vat()                                     # idempotent schema
def compute_vat_return(period_start, period_end)   # → dict of 9 boxes
def finalise_vat_return(return_id, by)             # locks the numbers
def list_returns()
```

`compute_vat_return` queries `gl_journal_lines` over the date range:

- **Box 1** = sum of credits to 2200 VAT Output minus debits (refunds
  reverse the original)
- **Box 4** = sum of debits to 1300 VAT Input minus credits (after
  partial-exemption adjustment, see Phase 2)
- **Box 6** = sum of credits to 4xxx revenue accounts (from the same
  date range, excluding exempt revenue accounts) — the net of
  taxable sales
- **Box 7** = sum of debits to 5xxx expense accounts (excluding
  payroll-equivalent accounts) — net of taxable purchases
- **Box 2 / 8 / 9** = zero for v1 (EU rules irrelevant
  post-Brexit for most institutions; populate when needed)

**GUI tab**: a "VAT Returns" sub-view (admin-only) lists computed
returns with status, can finalise or export to CSV for submission via
external bridging software.

Phase 1 cost: ~1 week.

### Phase 2 — Partial exemption

A configuration table that records the institution's recovery
percentage by activity, plus a year-end adjustment journal generator.

**New tables:**

```sql
CREATE TABLE vat_partial_exemption_rates (
    fiscal_year         INTEGER NOT NULL,
    recovery_percentage REAL    NOT NULL,           -- e.g. 0.18 for 18% recovery
    method              TEXT    NOT NULL,           -- 'standard' | 'special_method' | 'sector'
    set_by              TEXT,
    set_at              TEXT    NOT NULL DEFAULT (datetime('now')),
    notes               TEXT,
    PRIMARY KEY (fiscal_year)
);
```

**Year-end flow:**

1. Auditor / finance team computes the actual recovery percentage
   per HMRC rules (sales-based, sector-based, or special method).
2. The percentage is recorded in `vat_partial_exemption_rates`.
3. `compute_partial_exemption_adjustment(fiscal_year)` reads all input
   VAT posted in the year, multiplies by `(1 - recovery_percentage)`,
   and produces the adjustment journal:

   ```
   Dr  <expense accounts in proportion to where input VAT originally posted>
   Cr  1300 VAT Input
   ```

   (Moving the irrecoverable portion of input VAT from VAT-recoverable
   to permanent expense.)

4. The adjustment is timestamped and idempotent on
   `(fiscal_year, source_type='partial_exemption')`.

This requires ADR 0014 (AP) to be in place because input VAT only
materially exists once supplier invoices are flowing. Phase 2 can be
written in advance of any input-VAT activity — it just won't have
much to adjust until then.

Phase 2 cost: ~1 week (small code, accountancy decision is the
load-bearing part).

### Phase 3 — HMRC MTD API integration

**Out of scope for the first VAT build** but documented here so the
later integration has a target.

Required pieces:

- **OAuth 2.0 dance** with HMRC sandbox first, then production.
  Refresh tokens stored encrypted.
- **Fraud headers** (HMRC's "Tx-Monitoring" headers) populated from
  client OS/browser metadata — required for production submission.
- **API endpoints**:
  - `GET /organisations/vat/{vrn}/obligations` — list periods due
  - `POST /organisations/vat/{vrn}/returns` — submit
  - `GET /organisations/vat/{vrn}/returns/{period_key}` — retrieve
  - `GET /organisations/vat/{vrn}/payments` — see what's paid
  - `GET /organisations/vat/{vrn}/liabilities` — see what's owed
- **Application registration** with HMRC Developer Hub (production
  application requires a sign-off / penetration test from HMRC).
- **Dual-key submission**: only finalised returns are submittable; a
  submission attempt that fails leaves the return in `final` status
  (not `submitted`) and an error log row.

Phase 3 cost: ~3 weeks plus the HMRC application/test cycle (which
can take 2–4 weeks of calendar time but minimal engineering).

### Classification refinements (any phase)

The 8.117.118 `_VAT_DEFAULT_BY_SOURCE` map needs finance-staff review.
Specific cases to confirm:

| Source / activity | Current default | Likely correct |
|-------------------|-----------------|----------------|
| `research_grants` | exempt          | varies — funder-specific |
| `housing` (commercial guests) | exempt | standard — needs an explicit override at write-time |
| Conferences (no source_type yet) | n/a | standard for external paying delegates; may be exempt for academic conferences |
| Adult ed / CPD courses | n/a | standard or exempt depending on regulatory body |
| Room hire | n/a | standard (commercial) or exempt (educational) |
| Sponsorship income | n/a | standard |
| Charity shop second-hand | standard | margin scheme — special calc |

A simple sweep through the codebase to look for revenue paths that
don't currently have a `source_type` (or have a default-falling-through
one) is a good first step before formalising the map.

## Consequences

### Positive

- Trial balance shows correct VAT Output liability from forward-going
  activity (already true since 8.117.118)
- VAT returns can be produced from the GL automatically (Phase 1)
- Partial-exemption irrecoverable VAT recognised in the right
  expense category (Phase 2)
- MTD compliance achievable without external bridging software
  (Phase 3)
- Audit trail per VAT return: every Box figure is traceable to GL
  journals

### Negative / trade-offs

- **Accountancy decisions before code.** The classification refinements
  table above isn't decidable by engineers — needs finance-staff
  input plus probably an external auditor sign-off on the
  partial-exemption methodology.
- **Backfill is awkward.** Pre-8.117.118 journals are VAT-blind. They
  shouldn't be retrospectively split because the VAT decision
  depends on knowing the supplier's VAT registration and the
  activity classification — both of which the historical data lacks.
  Practical answer: VAT returns only cover periods starting on or
  after the change-over date.
- **MTD application cycle** is a non-engineering process delay.
- **Phase 2 depends on AP being in place** (ADR 0014). Until input
  VAT materially exists, partial exemption is theoretical.
- **The reverse-charge rules** (services from non-UK suppliers
  require self-accounting for output and input VAT on the same
  invoice) are genuinely complex and depend on AP + multi-currency.
  Out of scope of all three phases here.

### Neutral

- The data layer (8.117.118) doesn't change in any of the three
  phases. Each phase reads from / writes to the same `vat_rate` /
  `vat_amount` columns and the same 1300/2200 GL accounts.

### Open questions to resolve before implementation

(Phase-specific — answer in order of phase commissioning.)

**For Phase 1:**

1. **Quarterly period definition** — calendar quarter or non-standard
   accounting quarter? Most institutions use HMRC's stagger-allocated
   period (could be Apr-Jun or May-Jul depending on the VAT
   registration).
2. **Box 6 / Box 7 boundaries** — which revenue accounts are in
   "taxable sales" vs "exempt sales"? Schema needs a flag on
   `gl_accounts` or a hardcoded list in the report.
3. **Refunds treatment** — UK rules: refunds reduce Box 1 in the
   period of the refund. Already the natural outcome of how
   `post_refund` posts; documented for clarity.

**For Phase 2:**

4. **Partial-exemption method** — standard, sector, or special
   method? Most universities use either sector-based or a HMRC-
   approved special method specifically designed for HE.
5. **Recovery-percentage application timing** — apply the prior
   year's percentage to current-year input VAT (provisional), then
   true-up at year-end? Or wait for actual figures? The HMRC
   default is provisional + true-up.

**For Phase 3:**

6. **HMRC application registration** — needs a Government Gateway
   account, application via Developer Hub, and a penetration test
   from HMRC for production access.
7. **VRN (VAT Registration Number)** — single VRN for the whole
   institution or VAT group with multiple VRNs?
8. **Fraud headers** — client metadata (browser/IP) is required by
   HMRC; harvesting it from a desktop Tk app is non-trivial. May
   need a small web wrapper for the submission step alone.

These should be answered with finance staff (and external auditor)
before each phase begins.

### Estimated build cost (cumulative)

- Phase 1 (quarterly return): ~1 week
- Phase 2 (partial exemption): ~1 week
- Phase 3 (MTD API): ~3 weeks code + 2–4 weeks calendar for HMRC sign-off
- Classification refinement sweep: ~3 days, finance review needed

**Total**: ~5–6 weeks of engineering plus the MTD HMRC application
calendar time. Phases can be staggered.
